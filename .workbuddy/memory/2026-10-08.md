## 三阶段：真机排障「突然 401」+ 修复 token 淘汰策略

现象：CLI 一直报 `unauthorized`，但设备端没动过任何东西——其实是
`aiface_auth.xml` 里已有 **32/32** 个 token，CLI 手里那个是 9/22 签发的（还剩 13 天才过期），
被挤掉了。

根因（`app/src/main/java/com/aiface/app/Auth.kt`）：
`issue()` 在满 32 个时按 **最快过期** 淘汰 = 按签发时间从老到新杀。今天反复跑验证脚本
刷出一批新 token，最老的（正是长期在线的 CLI）第一个被踢。

修复：token 存储加签发时刻 → `<token>:<过期时刻>:<签发时刻>`，满额时改淘汰 **最新签发** 的。
这样刷 /auth 的客户端每次都淘汰它自己上一个，最多占 1 个名额，存量会话不受影响。
旧的两段式格式按「过期时刻 − TTL」反推签发时刻，**升级不会把已登录 agent 踢下线**（已实机验证）。

### 排障要点（下次直接复用）
- 突然 401：先看设备 `aiface_auth.xml` 里 token 数是不是打满 32，别急着重设密码。
- 恢复最快的路径是用 `scripts/adb-token.sh`（不用知道密码）。
- 反过来写设备（把 CLI 的 token 推回 shared_prefs）**不可靠**：App 进程内有 cache，
  写盘后必须 force-stop 重启才生效，很容易白改。
- 写 prefs 注入测试密码时，**先把 `pwd_salt`/`pwd_hash` 摘掉**——`Prefs.checkPassword` 有盐就
  只看加盐分支，注入的旧格式 `pwd` 会被无视（E/F 两组都已加固）。
